# S5 — 文档评审清单与责任分工

> 适用范围：所有涉及文档的 PR 评审。
> 原则：文档评审不是"挑字眼"，而是**确认读者能正确使用你写的东西**。

## 1. 评审角色

| 角色 | 关注点 | 是否必须 |
|---|---|---|
| 作者（Author） | 内容准确、示例可运行 | — |
| 技术评审（Tech reviewer） | 与代码一致、技术结论成立 | 必须（G1 门禁之外的人） |
| 可读性评审（Reader） | 术语一致、表述清晰、链接可达 | 建议；作者可兼任但需说明 |
| 规范评审（Doc owner） | 符合 S1–S4 | 仅当涉及规范变更或新增文档类型 |

**规则**：技术评审与可读性评审**不应是同一人**（除非 PR 只改错别字）。作者不能自审自己的文档。

## 2. PR 描述必须包含

```markdown
## 文档变更
- 涉及文档：docs/xxx.md（type=architecture，status=draft→active）
- 对应代码 PR：#123 / 本 PR 内
- 目标读者：（使用该模块的开发者 / 维护者 / 新人）

## 自检
- [ ] 元数据字段齐全
- [ ] 代码示例已在本地跑通
- [ ] 无真实凭据
- [ ] 链接全部可达
- [ ] 事实未与其他文档重复

## 需要评审人重点看
- 第二节的线程模型描述是否与实现一致
```

## 3. 通用评审清单

### 3.1 内容层

- [ ] 文档的目的单一，可归入 Divio 四分类之一
- [ ] 首段说明读者读完能得到什么
- [ ] 事实与代码一致（关键 API 签名、配置键默认值、模块依赖方向）
- [ ] 没有与其他文档重复的"事实"（重复的应是链接）
- [ ] 版本相关的行为标注了版本门槛
- [ ] 失败路径有说明（错误信息样例 + 处置方式）

### 3.2 可用性层

- [ ] 示例可运行，作者已在干净环境验证
- [ ] 命令标注执行目录与预期输出
- [ ] 术语符合 S2 §3.1
- [ ] 表格有明确表头与真实默认值
- [ ] 图片有图注，alt 文本独立可懂
- [ ] 链接文本可独立理解（无"点击这里"）

### 3.3 规范层

- [ ] 元数据头字段齐全、`id` 唯一、`type` 与目录匹配
- [ ] `status` 正确反映真实状态
- [ ] 废弃文档填写了 `superseded_by` 且有顶部提示
- [ ] 文件名 kebab-case，H1 与文件名一致

### 3.4 安全层

- [ ] 无真实凭据、token、内部主机名、真实客户数据
- [ ] 报文样例已脱敏

## 4. 专项清单

### 4.1 新增模块 README

见 [S1 §4 模块文档最小信息集](01-doc-structure-and-naming.md#4-模块文档最小信息集) 的 8 项，缺一即打回。

### 4.2 新增 ADR

- [ ] 记录了**当时的约束**（当时有哪些选项、为什么选了这个）
- [ ] 明确写出**被否决的方案及原因**（这是 ADR 最大的价值）
- [ ] 标注了**后果**（带来什么代价）
- [ ] `status` 为 `accepted` 且不再修改结论
- [ ] 取代旧决策时，新 ADR 的 `supersedes` 指向旧 ADR 的 `id`

### 4.3 修改既有文档

- [ ] 是否需要更新 `updated` 字段
- [ ] 是否产生新的版本影响（需要更新 S4 §5 清单中的其他文档）
- [ ] 被链接该文档的其他文档是否需要同步（改名/移动时）

### 4.4 废弃或取代文档

- [ ] 新文档已存在且 `status: active`
- [ ] 旧文档 `status: deprecated`、`superseded_by` 已填
- [ ] 旧文档顶部有废弃提示
- [ ] 所有指向旧文档的链接已更新（内链门禁 R6 兜底）

## 5. 评审意见的分级

避免"意见洪水"。分级标注：

| 标记 | 含义 | 作者处理 |
|---|---|---|
| `must` | 必须修改，否则不予合并 | 必修 |
| `should` | 建议修改，作者可选择保留并说明理由 | 酌情 |
| `nit` | 措辞细节，不阻塞 | 可选 |
| `question` | 评审人不确定，需作者澄清 | 需回复 |

**禁止**：在 PR 中留下无标记的意见，让作者猜哪些是必须的。

## 6. 评审时效

| 事项 | 时限 |
|---|---|
| 首次响应 | 1 个工作日 |
| 文档 PR 完成评审 | 2 个工作日 |
| 阻塞性 `must` 意见响应 | 1 个工作日 |

超时由文档 owner 催办或改派评审人。

## 7. 评审的反模式

| 反模式 | 为什么有害 | 正确做法 |
|---|---|---|
| 逐句润色而不指出实质问题 | 淹没真正的问题 | 先看 M1–M5（技术/可读性/去重/安全），最后才抠措辞 |
| "文档不够详细" | 无可执行性 | 指出**缺了哪个具体信息**、读者会在哪卡住 |
| "加个图" | 图不解决信息缺失 | 先确认缺的是关系还是量级，再决定图/表 |
| 评审人自己重写一遍 | 成本高、口径易变 | 给结构和必填信息，作者填内容 |
| 用"nit"淹没 `must` | 作者无法排优先级 | 严格分级 |

Architecture Decision · pw-reports / DEV-V5

报告与 Jenkins 构建号绑定方案

让每一次 Jenkins 构建的报告、manual/auto 用例结论、失败补图与人工标记，都归属于同一个 BUILD_NUMBER——而不是散落在本地 target/reports 与某台电脑的浏览器里。

版本 v1.0 日期 2026-11-04 范围 pw-reports · ReportServer · Jenkins 基线 1406 测 / 0 失败 / 6 skipped

结论先行

  1. 框架并不缺「拿到 build number」：ReportView 已解析 Jenkins 变量并渲染顶栏徽章，ReportServer 上传接口已支持 ?build= 并以 build 号作 runId，补图 / 标记 / 撤销三个 API 已落盘且非破坏性可还原。零件齐了，缺的是把它们串起来的三步。
  2. 真正的断点在三处：报告元数据不带 build 身份、CI 侧没有「打包上传」这个动作、Jenkins 页面没有该 build 的报告入口与人工复核回写。
  3. 因此本方案不重写报告，只做一件事：把 BUILD_NUMBER 提升为报告运行键——报告内容落在 /{project}/{BUILD_NUMBER}/，对外可见的地址始终是 Jenkins 自己的 ${BUILD_URL}PW%20Report/；人工补图与标记只写该 case 的 json，天然归属该次构建。

缺口：为什么「依附 build」这件事现在做不到

#缺口证据（当前代码事实）后果

02绑定模型：BUILD_NUMBER 作为「报告运行键」

不要为 Jenkins 单独造一套报告。只把已有的 runId 语义收紧为「一次 build = 一个 run」，三段落点自然对齐。

图 1 · 三层绑定模型：采集（身份）→ 归档（归属）→ 回写（可见）

三层各自解决一个不同的问题，不能互相替代：采集解决「报告自证身份」，归档解决「报告归属哪次 build」，回写解决「人在 Jenkins 页面能不能看见」。少任何一层，都会退化成现在的手工搬运。

表 3 · 改造清单（P0 = 打通主链路；P1 = 回写与人工结果归 build、影响面收敛）

不做什么

不改 ReportBus 事件流、不动 sink fan-out、不替换 Thymeleaf/FreeMarker 模板、不给报告加数据库。build 绑定是「路径 + 元数据 + 一个 HTTP 调用」，不是新架构。

为什么用 runId 而不是加字段

ReportServer 的目录布局 {root}/{project}/{runId}/ 本身就是最强的绑定：截图、trace、HTML、junit 全在同一目录下。以 build 号作 runId，物理归属即逻辑归属，不需要额外索引。

唯一不可妥协点

报告必须由 ReportServer 托管才能标记落盘。HTML Publisher 只是静态快照，任何「在快照上标记并回写」的方案都会退化成 localStorage——这一点在 §6 展开。

04Jenkinsfile：四步把 build 接上

Windows agent + Declarative Pipeline。四件事缺一不可：喂 junit、上传报告、留静态快照与截图、写 description。命令全部可直接复制。

Jenkinsfile（仓库根，Windows agent）可直接落地

// Jenkinsfile — pw_automation_framework / DEV-V5
pipeline {
  agent { label 'windows && jdk21' }
  options {
    timestamps()
    buildDiscarder(logRotator(numToKeepStr: '50'))
    // 同一 job 串行：避免两个构建同时写同一个 build 号目录
    disableConcurrentBuilds()
  }
  environment {
    PW_PROJECT       = 'pw-automation'
    // 只在服务端用（上传 + 写 API）；对外链接一律用 BUILD_URL
    PW_REPORT_SERVER = 'http://reports.internal:8080'
  }
  stages {
    stage('Test') {
      steps {
        bat 'mvn -f pom.xml test -Dcheckstyle.skip=true'
      }
      post {
        always {
          // ① Jenkins 原生测试趋势：吃框架已产出的 pw-junit.xml
          junit testResults: 'pw-reports/target/reports/pw-junit.xml',
                allowEmptyResults: true, skipPublishingChecks: true
        }
      }
    }
    stage('Publish Report') {
      steps {
        // ② 上传：runId = BUILD_NUMBER，得到 /{project}/{N}/
        bat '''java -cp pw-reports/target/pw-reports-1.0.1.jar ^
          com.hsbc.cmb.hk.dbb.automation.framework.report.cli.ReportUploader ^
          --dir pw-reports/target/reports ^
          --server %PW_REPORT_SERVER% --project %PW_PROJECT% --build %BUILD_NUMBER%'''

        // ③ 静态快照兜底 + 产物留档（Jenkins 页面直接可见）
        publishHTML target: [
          reportDir: 'pw-reports/target/reports',
          reportFiles: 'index.html',
          reportName: 'PW Report (snapshot)',
          allowMissing: true, alwaysLinkToLastBuild: false, keepAll: true
        ]
        archiveArtifacts artifacts: 'pw-reports/target/reports/**/screenshots/*.png,' +
          'pw-reports/target/reports/pw-summary.json,' +
          'pw-reports/target/reports/**/trace.zip',
          allowEmptyArchive: true

        // ④ 回写 description：用 Jenkins 内置对象，不需要 HTTP、凭证或 crumb
        script {
          def sum  = new groovy.json.JsonSlurper().parseText(
                       readFile('pw-reports/target/reports/pw-summary.json'))
          def t    = sum.totals
          def text = "PASS ${t.passed} / FAIL ${t.failed} / SKIP ${t.skipped}"
          if (sum.manual) { text += " | manual ${sum.manual.total} (pass ${sum.manual.passed}, fail ${sum.manual.failed})" }
          text += "\n${env.BUILD_URL}PW%20Report/index.html"
          currentBuild.description = text
        }
      }
    }
  }
}

表 4 · Jenkins 四步各自的不可替代性

Jenkins 要登录，回写要不要凭证

不需要。Pipeline 本身就跑在 Jenkins 里，currentBuild 是内存对象，赋值不走 HTTP，也不校验登录态、不需要 crumb、不碰 CSRF。currentBuild.description = text 一行即完成。这也是为什么 ④ 段不用 withCredentials。

什么时候才真的需要凭证

只有「Jenkins 之外的进程要改 description」时才需要：比如人工补图后由报告站刷新 build 描述。这时用专用服务账号 + API Token（不是密码、不是浏览器 session），存 Credentials 由 withCredentials 注入；个人 token 会随轮换/离职失效，不建议。

SSO 环境最容易踩的坑

公司 Jenkins 前面常挂统一登录。若 BUILD_URL 是代理域名、而 token 属于直连端口，取 crumb 时会 401/403。规则：取 crumb 与提交 description 必须用同一个 host、同一个端口；代理域名下的 token 交给平台管理员开白名单。

Freestyle / 脚本式替代（不用 Jenkinsfile）

如果暂时不能改 Jenkinsfile，用「Execute Windows batch command」两个步骤即可达到同样效果：

:: 步骤 1 — 打包报告目录
powershell -NoProfile -Command "Compress-Archive -Path 'pw-reports\target\reports\*' -DestinationPath 'report.zip' -Force"

:: 步骤 2 — 以 build 号为 runId 上传
curl -X POST "http://reports.internal:8080/pw-automation/runs?build=%BUILD_NUMBER%" --data-binary "@report.zip" -H "Content-Type: application/zip"

:: 然后照旧添加 Post-build Actions：Publish JUnit test result report（pw-reports/target/reports/pw-junit.xml）
:: 以及 Publish HTML reports（pw-reports/target/reports / index.html）

表 5 · 静态快照与托管报告的差别（前者只适合留档，后者才支持人工闭环）

API 契约（服务端已实现，前端已对接）

端点请求体语义与副作用
POST /{project}/{runId}/api/patch {outcomeId, note, screenshots:[{filename,dataBase64}]} base64 解码写 screenshots/yyyyMMdd-HHmmss-NN.png，并作为步骤追加进该 case 的 {pid}.json；随后只重渲染该 case 的 HTML 并更新聚合，其他 case 不动。
POST .../api/mark-success {outcomeId, note} 首次标记暂存 originalResult / originalTestFailure* 后覆盖为通过；可重复调用改备注，不清原始态。
POST .../api/mark-revert {outcomeId} 用 original* 无损还原失败态并清空覆盖标记；未标记过时返回 409。

幂等

同一 build 重复上传使用 REPLACE_EXISTING，重跑即覆盖为该 build 的最终报告——语义正确：一个 build 只有一份结论。

并发

不同 build 落在不同目录，天然隔离；同一 job 由 disableConcurrentBuilds() 串行，避免同号并发。

不做额外验证

补图与标记不引入 token、登录或二次确认，请求到达即写 {pid}.json。边界交给网络：服务只在内网、只监听内网网段。能连上这个端口的人就能改结论——这是明确的取舍，不是遗漏。

补图与标记的影响面：只碰当前 case

json 是唯一数据源。补图与标记只改两样东西：该 case 的 {pid}.json（结论、original*、evidence、截图引用）和该 case 的 screenshots/；HTML 全部是渲染产物，删了也能由 json 重建。要求是「一次操作只影响当前那一个 case」，而代码里 reindex() 做的是整个 run 的全量重建：递归读全部 outcome → 逐个重渲染所有 case 的 HTML → 重写 summary / index / csv / junit。数据没串，但写入面被放大了。

动作写入的文件其他 case 的 jsonbuild 聚合统计junit 原始结果
POST api/patch {runId}/{pid}/{pid}.json、{pid}/screenshots/*.png、以及 reindex 带来的全量 HTML 不改 字节不变 重算（manual 计数变） 现状会被重写
POST api/mark-success 同上，且只在该 case 上暂存 original* 不改 重算（pass 数 +1） 现状会被污染 失败数被改小
POST api/mark-revert 同上，用 original* 还原并清覆盖标记 不改 重算（回到原始） 同左

补图表 · 目标语义：数据层只碰当前 case，聚合层必须更新，junit 只反映机器执行

已经隔离的：数据层

三个 API 都只读写 runDir/{pid}/{pid}.json 与该 case 的 screenshots/。标记用 original* 暂存原始态，mark-revert 可无损还原——不会串到别的 case。

没有隔离的：渲染层

一次标记会把该 run 下所有 case 的 HTML 重写一遍。内容虽相同，但在 4 线程池并发下，其他 case 页可能被读到半截——因为除 JsonWriter 外，渲染器都是 Files.writeString 直接覆盖，没有临时文件 + 原子替换。

必须扩散的：聚合层

pw-summary.json / index.html / cases.csv 必然要变——build 级结论必须反映人工复核，这不是污染。但要限定在该 run，不跨 build。

把影响面收回到当前 case（P1 代码改造，3 处）

① 拆分 reindex：case 级 / 聚合级 分开JAVA

//  现状：reindex(runDir) 遍历所有 json + 重渲染所有 case HTML

private void reindexAggregate(Path runDir) throws IOException {  // 只碰聚合产物

    JsonWriter.writeSummary(runDir, all);
    AggregateBuilder.writeIndex(runDir, all);
    CsvWriter.writeCsv(runDir, all);
    JunitXmlWriter.writeXml(runDir, all);                      // 用 original* 还原后生成
}

② 同 run 串行、异 run 并行（保住 4 线程吞吐）JAVA

private final ConcurrentHashMap<String, ReentrantLock> runLocks = new ConcurrentHashMap<>();
private ReentrantLock lockOf(String key) {                  // key = project + "/" + runId
    return runLocks.computeIfAbsent(key, k -> new ReentrantLock());
}

③ 所有渲染器统一原子写（tmp + ATOMIC_MOVE）JAVA

static void writeString(Path target, String content) throws IOException {
    Path tmp = target.resolveSibling(target.getFileName() + ".tmp");
    Files.writeString(tmp, content, StandardCharsets.UTF_8);
    try { Files.move(tmp, target, REPLACE_EXISTING, ATOMIC_MOVE); }
    catch (AtomicMoveNotSupportedException e) { Files.move(tmp, target, REPLACE_EXISTING); }
}

顺序很重要：先写 case 级（最坏只影响自己），再在 run 锁内更新聚合层；junit 生成时优先取 originalResult，人工标记不进 junit。

两个语义边界，落地时别混：

  • 标记≠执行：mark-success 只改结论层（summary / index / csv / description），不改 pw-junit.xml 里的机器结果。否则 Jenkins 测试趋势会被人工操作篡改，审计时无法解释「为什么这次构建失败数突然变少」。
  • 只影响本 run：聚合重算的输入是 runDir 内的 case，不读其他 build 目录。第 42 次构建的标记永远不会改写第 41 次构建的任何文件。

  • V1 · 身份落盘：mvn test 后 pw-summary.json 含 build.number，且与 %BUILD_NUMBER% 一致；本地无该变量时 build 段为 null/absent，不伪造。
  • V2 · 归属正确：从 build 页点 PW Report 能打开，顶栏构建徽章即该 build 号；换一个 build 号再上传，两个目录互不覆盖。
  • V3 · Jenkins 可见：build 页面出现 test trend（junit）、"PW Report (snapshot)" 链接、artifacts 中的失败截图。
  • V4 · 标记持久：在托管页补图 + 标记通过 → 刷新仍生效；mark-revert 后恢复失败态；pw-summary.json 的 manual/overridden 计数同步变化。
  • V5 · 回写生效：build description 显示「PASS/FAIL/SKIP + manual 统计 + 报告 URL」，链接可点开直达该 build。
  • V6 · 失败不阻断：ReportServer 不可达时，测试本体仍为原结果（不为报告服务背锅）；--soft 模式下构建不因上传失败而变红，但日志有明确告警。
  • V7 · 影响面隔离：标记 case A 后，{runId}/ 下除 A 以外的 {pid}.json 与 {pid}.html 的 SHA-256 与 mtime 均未变化；pw-summary.json / index.html 有变化属预期。pw-junit.xml 中 A 的失败数不应因人工标记而减少。

表 8 · 节点重启影响矩阵（判据：服务是否与 agent 同生命周期、root 是否在持久盘）

数据在磁盘，不在内存

报告是 root/{project}/{runId}/ 下的普通文件，进程重启不影响内容。所以「重启丢报告」几乎都是 root 放错了位置，而不是服务本身的问题。

上传不是原子的

ReportServer 先建 runDir 再逐条 Files.copy，中途被杀会留下缺 index.html 或半套截图的目录；同号再传只覆盖同名文件，上次多出来的脏文件不会被清。

无优雅停机

基于 com.sun.net.httpserver，没有 shutdown hook 与连接排空；重启会硬断正在处理的请求，客户端看到连接重置而不是 5xx。

加固项做法不做会怎样
数据目录--root D:\pw-report-data，绝对路径、独立盘、不进 workspace一次 mvn clean 或 agent 重装就清空全部历史
服务自启NSSM 服务 + AppExit Default Restart重启后所有报告链接 404，直到有人手动拉起进程
对外地址description / 通知只用 ${BUILD_URL}PW%20Report；服务地址仅服务端内部使用agent 换 IP 或服务迁移后，已经发出去的链接集体失效
上传原子性解压到 {runId}.tmp-<rand>，完成后 Files.move(ATOMIC_MOVE) 进最终目录；启动时清理残留 *.tmp-*重启撞上上传窗口 → 半成品报告，页面 404 或缺图
归档校验上传后 GET /{project}/{build}/pw-summary.json 必须 200，才算归档成功HTTP 200 不等于报告可用，失败被静默吞掉

构建中断语义接受「中断的 build 没有报告」；重跑产生新 build 号，不复用旧目录误以为要「补传」到同一个 build，反而覆盖掉下一次的结论

10一句话回答你的问题

「怎么依附当前 build number 的 Jenkins server」——不是把报告塞进 Jenkins workspace，而是让 BUILD_NUMBER 成为报告的目录键：测试结束把 target/reports 上传到 /{project}/{BUILD_NUMBER}/，对外只暴露 Jenkins 自己的 ${BUILD_URL}PW%20Report/；人工补图与标记只改该 case 的 .json（json 是唯一数据源），聚合统计随该 build 更新，最后把统计与这个链接写进 build description。这样「第 42 次构建的报告、第 42 次构建的人工结论」在物理路径上就是同一件事，对外地址也只有一套。

1. 设计目标与五条企业级原则

目标：用户以业务流程（自然语言 / 录制骨架 / DSL）描述要做什么，框架指挥浏览器逐步执行、自动发现并验证元素定位器、生成可提交、可回归、可维护的 Step 业务代码（Feature + Glue + Page Object）。

原则含义与判定标准
P1 · 证据驱动观察浏览器状态以运行时可访问性/DOM 证据为依据；ref 仅作短期句柄，不能作为持久定位器。每一步「先观察、后动作、再回读」；快照不是对页面真实状态的完整证明。
P2 · 可重复决策LLM 只产出受 schema 约束的意图与候选；执行由确定性 StepDriver 承担。在固定版本、受控数据和相同外部条件下，决策及记录应可比较；不承诺浏览器/业务结果必然一致。重试按动作语义约束，非幂等写操作不得自动重放。
P3 · AI 与运行时分离生成 Step 代码落库后，回归运行时零 LLM 依赖（借鉴 MCP 官方理念：committed tests are the durable artifact）。LLM 只存在于「设计期/生成期」。
P4 · 最小权限与纵深防御MCP 官方明示「不是安全边界」；本设计采用数据最小化、原语分级、凭据隔离、上下文隔离及网络出站策略。应用层 allow-list 不是网络安全边界，须由受控网络/代理策略兜底。
P5 · 全链路可观测每步记录最小必要 trace（步骤 id、策略版本、耗时、结果及脱敏摘要）；失败即停止并提供最小现场。仅在隔离靶场支持受控重放，审计记录本身不可直接重执行。
与「生成可维护代码」的关系：候选定位器须经过语义与业务期望校验、人工/受控审批后才能进入生成流程；生成物经格式/静态检查、编译、隔离靶场测试和代码评审后才合并。指纹和 trace 是辅助证据，不证明定位器唯一、正确或长期稳定。

录制/代码生成：上游提供多语言录制/代码生成功能，包括 Java 生成模式只参考用户体验和输出形态是否生成 Java/JUnit 代码由本项目当前 JUnit4/Cucumber Runner、模板和维护要求决定；须单独验证兼容性
任意代码执行：上游提供高风险代码执行工具，并明确提示风险不将其纳入本产品原语产品面不暴露通用 evaluate/run-code 能力；需要诊断时提供受限类型化接口
安全声明：上游文档说明部分配置不是安全边界不将上游工具配置视为安全控制本方案仍须采用应用策略、身份授权、运行隔离和企业网络出口控制；单独的 redirect 校验不是充分安全边界
会话策略：上游支持 persistent/isolated 等不同配置选项借鉴显式选择隔离策略本项目须明确 context/page 所有权、登录态注入、并发与清理语义；不能假设 ConcurrencyGate 自动提供浏览器隔离
上下文注入点：上游支持注入既有 BrowserContext把注入作为可评估的集成方式具体是否适合本项目，须核验 BrowserStartupImpl/SessionStore 生命周期后决定，不直接移植上游语义
探索用 Agent、回归用提交的测试（提交的测试可在回归期脱离 Agent）参考设计理念目标是生成/批准后 CI 零 LLM；需通过构建与运行测试证明，不能由架构声明替代验证
结论：上游实现提供了可借鉴的快照、工具原语和录制体验，但并不能证明本方案的正确性、稳定性或安全性。这里仅把它作为设计参考；本项目的协议、策略、能力范围和运行器须按自身 API、威胁模型与验收数据确定。

资产不仅要能生成代码，更要能驱动验证：用已落库（active 或 pending_review）的资产——尤其是联动图谱与行为模型——在隔离靶场直接驱动浏览器执行资产定义的操作/联动序列，验证：① 元素清单的定位器真实命中（稳定性）；② 行为模型预期结果类别成立（如"提交→跳转"）；③ 联动图谱可复现（操作 A → 元素 B 状态变化）。这区别于路径 C（资产→CodeGen→完整工程→mvn test 回归），是轻量、即时的前置验证门禁，避免"生成了代码但联动断言根本不成立"。

最小实现的约定（与生产的差异，避免误读）：① ElementRef.refId 是业务/需求语义稳定 id（资产级主键），与运行期定位解耦；运行期定位由 locatorCandidates（LocatorSpec）按 Role-First 梯队承载，第一梯队即 role（getByRole(role,{name})）——这正是 Playwright 最稳健、官方首推的定位方式，也是 Playwright MCP 的无障碍树驱动思路。快照索引键与命令目标统一采用该 role 定位符的 canonical 串，天然与 CSS 解耦、抗 DOM 重构。生产系统沿用同一模型，仅增加 testid/id/text/css 回退与"候选逐级校验唯一性"。② LinkageGraphVerifier 在每轮重复前重新导航到目标页，确保各轮独立可重复（避免上一轮触发造成的状态残留），这是"稳定性统计"正确性的前提。③ REQUIRED 在断言里暂以 enabled 近似，真实实现须校验必填属性。

  • 幂等：同页面 + 同需求版本的重复分析可幂等更新 draft，不产生重复 active 资产。
  • 可观测/审计：每次分析、每次资产状态变更记录来源指纹、模型版本、操作者（R9）；trace 经自研 Report 落点。
  • 版本兼容：资产 schema 演进须向后兼容；旧版资产可归档读取，新字段可选；破坏性变更走版本号 + 迁移。

4.2 SnapshotTree —— 快照协议

每次快照返回有版本和资源边界的可访问性/DOM 观测结果。它是一个时间点的观测，不是页面完整真相。节点 ref 绑定到 context、page、frame 和 snapshotVersion；页面或 Frame 变化、动作导致 DOM 更新后必须重新快照。跨域 Frame、Shadow DOM、虚拟列表及不可访问节点须有明确的“不支持/部分观测”状态，不能静默猜测。

SnapshotEnvelope ::= {
  schemaVersion, contextId, pageId, frameId, snapshotVersion,
  capturedAt, truncated, nodeCount, byteCount, nodes: Node*
}
Node ::= {
  ref: "e12", role: "button", accessibleName: "新建订单",
  locatorCandidates: [{ kind: "role", role: "button", name: "新建订单" }],
  sensitivity: "PUBLIC|REDACTED|UNKNOWN", children: Node*
}
机制规则
ref 生命周期ref 仅在本次快照内有效；动作后必须 Re-snapshot 拿新 ref。代码生成永不使用 ref（同 MCP 官方规则：ref 是观察句柄，不是测试选择器）。
候选定位器协议只返回类型化候选描述，不返回可直接拼接执行/生成代码的任意 selector 字符串；由受信任的实现解析、转义并验证。
视口与边界默认限制视口、深度、节点数、字节数和生成时限；全页/子树须显式请求。超限返回截断标志和原因，不得误报为完整快照。
脱敏默认不向 LLM 发送任意页面内容。快照生成、模型请求、异常、URL、网络摘要和 trace 共用集中脱敏/字段白名单；未知敏感级别按敏感处理。凭据由独立 secret provider 按引用注入执行器，原文不进入 StepPlan。
快照指纹语义摘要仅用于比较诊断，不作幂等证明、身份认证或跳过动作的依据；指纹应按数据分类避免包含敏感内容，并记录算法版本。
实现映射（v2.0）：落地代码中的 Snapshot 由 page.ariaSnapshot() 解析生成，节点 ref 即 LocatorSpec 的 canonical 串（role 优先，如 role=checkbox;name=I agree to the terms）。这与 MCP 的"ref 仅本次快照有效、禁止用于代码生成"不同：本框架把稳定、语义化的 role 定位符作为资产级索引键，使业务资产与易变 CSS 解耦，同时保持只读、数据最小化（R1/R7）。隐藏元素（如 display:none）不进入 ARIA 树，天然支撑 APPEAR/DISAPPEAR 断言；禁用态以 [disabled] 标注驱动 ENABLE/DISABLE 断言。
多语言注意：快照里的 accessibleName 是当轮语言的渲染结果，因此快照 canonical 只能是字面文案（如 role=checkbox;name=我同意条款）。资产要跨语言复用，索引键不能直接用这个 canonical，而应先用 NLS key 解析成当轮文案再查（见 §4.7）——否则"某语言下全部查不到"，且报错完全指不到语言问题。

4.3 意图翻译与 StepPlan

三源归一为版本化、受 schema 约束的 StepPlan；schema 是输入验证的一层，不是完整的安全边界。每种 ActionType 使用独立参数结构和约束：例如 navigate 不要求 locator，snapshot 不要求 expect；有副作用动作须声明执行策略、超时和允许的业务后果。未知字段默认拒绝，未知 ActionType、非法参数和越权 origin 均拒绝。

意图源机制适用
录制骨架现有Codegen 录制一次业务流程 → 结构化动作序列作为确定性骨架；LLM 只做「补全泛化」（变量参数、断言、异常分支）。核心回归路径（确定性最高，首选）
自然语言新增LLM 翻译「登录→进入订单管理→新建订单」→ StepPlan；输出经 schema 校验 + 可执行性预检（首步 navigate 是否可达）后放行。探索新路径 / 一次性场景
结构化 DSL新增YAML/JSON 步骤声明（action/target/params/expect），逐条校验后直接执行；零 LLM 依赖。稳定流程的显式表达 / CI 注入

审批授权 · 按业务后果分级（P4 首刀）

只有状态机还不够：旧 approve(id, approver, appVersion) 只校验两个字符串非空，任何人可以批任何定位器。这留下四个真实缺口——批的不是眼前这份内容（定位符被改过，凭据上看不出来）、在测试环境批的拿去生产用（不绑定 origin）、一次审批永久有效（页面早改版，凭据还"活着"）、谁批的都算（没有业务后果分级，也没有职责分离）。因此审批结果改为一份可核对的授权凭据 ApprovalGrant，而不是一个名字。

组件职责 / 铁律
RiskTierLOW（可读性，1 人可自审 ≤180 天）· MEDIUM（流程走向，1 人须职责分离 ≤90 天）· HIGH（数据写入，≤30 天）· CRITICAL（资金/不可逆，2 人须职责分离 ≤7 天）。不提供默认档：若允许缺省，凡是"忘了标"的候选都会落进最松的档，分级退化成"谁漏填谁受益"。
ApprovalRequest审批人显式声明等级、origin、应用版本、审批人（可逗号分隔多人）、可选有效期与摘要。不接受"只给一个名字"的简写。
ApprovalPolicy八条规则全跑不短路：RISK_TIER_DECLARED / APPROVER_IDENTITY（占位符 manual/cli/system/true 不算人）/ APPROVAL_COUNT（同一人写两遍不算两人）/ SEPARATION_OF_DUTIES（审批人 ≠ 提出者；提出者未登记时拒绝，否则"不署名"就成了稳定的自批通道）/ PLAN_DIGEST / ORIGIN_BOUND（禁止 * 通配）/ APP_VERSION_BOUND / VALIDITY_WINDOW（超过等级上限即拒绝，不给关键定位器批一年）。
ApprovalGrant不可变凭据：candidateId · riskTier · planDigest · origin · appVersion · approvers · issuedAt · expiresAt。计划摘要 = SHA-256(targetRef + canonical + expectedRole) 前 16 位——不含证据：重新取证不该触发重新审批，否则人会开始嫌麻烦而绕过流程。
productionLocator / approvedLocator改为三参（targetRef, appVersion, origin），校验未过期 + origin 一致 + 版本一致 + 摘要一致 + 唯一命中。任一项不满足即返回空，过期不自动续期；无凭据的历史 APPROVED 记录一律不可回注。
# 资金类操作：两名审批人，职责分离，有效期 7 天
candidate approve --id cand-0001 --risk CRITICAL --approver "bob,carol" \\
                  --origin https://dbb-uat.example.com --app-version 2026.11.3 --note "工单 CHG-1024"
#   → 业务后果  : CRITICAL —— 影响资金/不可逆操作：2 人审批，须职责分离，≤7 天
#   → 计划摘要  : f73e34aa56aa2487        有效期至 : 2026-11-10 07:20:13Z

candidate locator --target transfer.confirm --app-version 2026.11.3 --origin https://dbb-uat.example.com
# 换环境 → 退出码 3：origin 不匹配（审批绑定 uat，请求 prod）
为什么不留"简写重载"：一旦存在 approve(id, approver, appVersion) 这种只给名字就能过的入口，上面的分级、职责分离、origin 与有效期绑定可以被一行调用全部绕过。API 层面直接删掉旧签名，CLI 层面把 --risk/--origin 设为必填——治理规则只有"没有旁路"才算生效。
旧库迁移语义：历史记录只有 approvedBy + approvalAppVersion、没有 approval 块，加载后 hasGrant()=false：审批人仍可展示（审计不断档），但回注一律为空，须重新审批。凭据字段损坏则整库读取失败——宁可读不出来，也不要悄悄当成"无审批"继续跑。
由测试钉住的语义（ApprovalPolicyTest 11 项 + CandidateLibraryTest/CandidateCliTest 扩展）：缺等级/缺 origin/缺版本各自命中对应规则；bob,bob 不算两人；MEDIUM 自审被拒而 LOW 自审放行并告警；未登记提出者的候选不得进入 MEDIUM 及以上；摘要不符即拒；* 通配不接受；有效期超上限即拒；过期后回注为空但状态仍为 APPROVED；换 origin 取不到；旧库无凭据不可回注。

4.5 稳定代码生成（四层产物 + 断言）

生成物与代码仓同构，生成后立即进入与手写代码相同的评审/编译/运行管线。借鉴 test-automation 既有分层（tests/glue · tests/steps · tests/pages），最终回归资产为 Feature / Glue / Steps / Page Object（＋ Assert）。关键澄清：录制工具（pw-codegen）在手动录取过程中只产出 Page Object + Steps（@Step 业务流）+ Assert 三类，并不生成 Feature 与 Glue；Feature 由业务需求驱动生成，Glue 由需求→代码绑定（P2）生成，二者与录制解耦。

产物来源内容落点 / 稳定性保障
Page Object录制（Tab1）定位器常量（已验证回注）+ 原子交互（type/click/readText/waitForVisible…）tests/pages；无业务流；方法带 trace javadoc（来源/指纹/验证时间）
Steps（业务流层）录制（Tab2）可复用业务方法（@Step 标注，如 登录 / 新建订单 / 切换 Profile）：由 Page Object 原子交互组合，承载跨页流转、session 管理、API mock 编排tests/steps；无定位器（只在 PO）；一个 Steps 方法被多个 Glue/场景复用
Assert（断言）录制（Tab3）与 Steps 会话一一对应的断言方法（assertN），读取页面状态做业务校验（与 test-automation 的 tests/verify/* 同性质）tests/steps 或独立 verify 包；纯读、无副作用
Feature业务需求驱动（非录制）业务语言场景（Given/When/Then），由 StepPlan 业务化改写而来resources/features；人工可读、可评审
Glue需求→代码绑定（P2，非录制）Cucumber @Given/@When/@Then 方法，仅做参数解包 + 委托 Steps（如 new LoginSteps().logon(env, user)）tests/glue；无定位器、无业务流（极薄，单一职责）
为何需要 Steps 层（区别于原“三层 Feature/Glue/PO”）：原设计把业务方法（登录、下单、跨页）塞进 Page Object，是“胖 PO”反模式。独立 Steps 层后：① Page Object 回归“只管元素”的单一职责；② 业务流在 Steps 内可复用、可单测、可跨场景共享；③ Glue 保持极薄、只做短语→方法映射。该 Steps 即录制工具 Tab2 产出的 @Step 类，与 test-automation 的 tests/steps/*Steps.java（如 LoginSteps/HomeSteps）同构。
录制 ≠ 四层一步到位：手动录取（pw-codegen）只落地 Page Object + Steps + Assert 三类脚本化产物；Feature 由业务需求生成、Glue 由需求→代码绑定生成（把 Feature 短语委托给录制得到的 Steps）。不要把 Feature / Glue 算作录制工具的输出，也不要在录制期强求 BDD 结构——录制产物经需求→代码绑定后，才组装成可跑 mvn test 的四层回归资产。
P2 绑定生成器已落地：FeatureGlueGenerator（pw-codegen · codegen.binding）——录制与需求两条产线在此汇合：录制的 Steps 类作委托目标，需求侧只描述场景。输入 FeatureGluePlan（feature 名 / 标签 / 场景 / 步骤关键字 / 短语（Cucumber 表达式）/ 参数声明 / feature 字面值 / 委托目标），经 FreeMarker 模板 feature.ftl + glue.ftl 输出两份文本，writeTo(featureDir, glueDir) 落盘。它不接入 MultiPageCodegen.build()，与录制互不污染。
生成期校验（不留到编译期）规则
占位符 ↔ 字面值数量必须相等，多一个或少一个直接抛 IllegalArgumentException
占位符 ↔ 参数类型{string}/{word} → String（feature 内加引号）；{int}/{long}/{double}/{float}/{bigdecimal}/{byte}/{short}/{boolean} → 对应 Java 类型（feature 内裸写并校验格式与取值范围）
注解表达式Glue 注解原样保留 {string} 占位符，绝不替换成字面值——否则 Cucumber 匹配不到 feature 行
命名派生文件名/类名由 feature 名派生（Role element login → role_element_login.feature / RoleElementLoginGlue）；方法名由短语派生，同场景重名自动加 _2 序号；import 只引实际用到的注解与 Steps 类
@When("I log on as {string} with role {string}")          // 注解 = Cucumber 表达式（占位符不动）
public void i_log_on_as_with_role(String username, String role) {
    steps.logon(username, role);                          // delegateForwarding(...)
    // 录制步骤无参时：steps.step1();（delegate("step1")，短语参数由 Steps 内部消化并生成注释）
}
P2 流水线入口：BindingCodegenPipeline + 计划 JSON——需求评审通过后，绑定关系以 JSON 提交进仓（BindingPlanJson：featureName / gluePackage / stepsClass / tags / scenarios；每个步骤含 keyword、phrase、params、args、delegate、forward），流水线 run(planFile, featureDir, glueDir) 依次完成「解析 → 生成 → 冲突守卫 → 落盘」，也可直接 run(plan, ...) / runJson(json, ...)。计划可 toJson 回写，便于评审 diff 与版本化。
落盘守卫（CodegenFileWriter）：只覆盖自己生成的产物。目标文件首行不含 GENERATED BY CodegenInspector V3 即视为手写代码，抛 CodegenConflictException；且先全查、后全写——Feature 可覆盖而 Glue 是手写时，两份产物一个都不写，不留下"Feature 已被冲掉、Glue 报错退出"的半截状态。
验证边界：本模块只保证「计划合法 + 安全落盘」，编译与冒烟由目标仓 mvn test / CI 执行，不在 pw-codegen 内伪造编译通过结论。

验证管线：模板生成 → 编译（checkstyle 同规）→ 冒烟执行（生成场景跑 1 遍）→ 落库。落库后即普通代码，回归运行时零 LLM（P3）。绑定产物与录制产物走同一条验证管线：Glue 编译不过或 feature 匹配不到步骤，都在冒烟阶段暴露。

4.6 LLM 页面理解与测试资产生成（分析期，非运行时）

除「自然语言→StepPlan」外，另一个明确依赖 LLM 的环节是页面理解。与单纯"看页面"不同，本环节必须结合需求上下文才能产出有用的测试资产：脱离需求的元素清单只是一堆 DOM 节点，只有把页面元素 / 操作 / 联动映射到需求条目与业务规则，资产才可被评审、可追溯、可度量覆盖度。它只发生在分析期 / 资产生成期，不进入运行时与回归期——回归仍零 LLM（§7 P4）。此环节与 R6「AI 无执行权」不冲突：LLM 消费的是只读、脱敏后的观测（需求上下文 + a11y 快照 + 网络摘要 + 受限诊断），全程不持有浏览器原语调用能力。

资产定义需求映射（须回链需求条目）来源与约束
① 元素清单
Element Inventory		页面可交互元素的角色、类型、稳定定位器候选（§4.4 梯队②/③）、可见文本、语义用途每个元素标注对应的需求条目 / 业务字段（如"转账金额输入框 ← REQ-101 金额录入"）；区分主流程元素与辅助元素来自 SnapshotTree（§4.2）；定位器候选走 §4.4 梯队④「AI 建议」铁律，必须验证后入库
② 操作行为模型
Behavior Model		每个元素的合法操作（click/fill/select/check…）、预期结果类别（无副作用 / 导航 / 异步 / 校验）、前置与后置业务断言操作对应需求里的业务步骤 / 验收标准（如"提交 → REQ-102 须返回成功且跳转结果页"）；断言须可对应验收点LLM 基于快照 + 交互观测 + 需求上下文推断；属「未验证建议」，需确定性校验与人工审批
③ 联动图谱
Linkage Graph		某元素操作后，哪些元素 / 区域发生状态变化（级联下拉、弹窗触发、禁用/启用、校验提示、列表刷新、金额计算等）联动对应需求里的业务规则（如"选'对公'→ 用途字段出现且必填 ← REQ-103"）；每条联动标注规则来源LLM 对比操作前/后快照差分 + 需求规则推断；是断言与场景编排的关键上游，避免人工逐条猜联动

需求上下文来源：需求文档 / 验收标准 / 用户提供的业务说明，或复用框架已有的 Cucumber Feature（Given/When/Then 即天然的需求载体）。需求文本作为 LLM 分析的上下文输入，同样须过白名单与脱敏（R1/R7）——需求样例中的真实账号、金额、PII 须遮蔽，不带入模型上下文。

需求溯源与覆盖度：三类产物落库时均记录关联的需求 ID / 验收点，形成「需求条目 → 页面元素 / 操作断言 / 联动断言」的可追溯链路；可据此统计需求覆盖度（哪些需求已有对应测试资产、哪些联动规则未被断言覆盖），使资产不仅是"能跑的代码"，更是"可审计的需求落地证据"。

落库为测试资产：三类产物（含需求映射）聚合成 Page Object 草案 / StepPlan 草案 / 联动断言草案，进入与手写代码相同的评审/编译/运行管线（§4.5）。AI 产出一律视为「未验证建议」，须经候选验证器（§4.4）+ 人工/受控审批后才升级为可信资产；无法确认时停止并转人工，不自动回退（§4.4 铁律）。

企业级资产生产流水线（可重复、可审计、可治理）：

阶段动作产出 / 门禁
① 需求接入解析需求上下文（Cucumber Feature / 需求文档），提取需求 ID、验收点、业务规则结构化需求模型；需求缺失则资产标记 incomplete，不阻断后续
② 页面观测在隔离靶场采集脱敏快照 / 网络摘要 / 受限诊断（白名单字段，R1/R7）只读观测包；敏感字段已遮蔽
③ LLM 理解模型基于「需求 + 观测」推断三类资产及需求映射候选资产（状态 draft）；模型不可用则降级到录制/手写，不阻塞
④ 确定性校验候选验证器（§4.4）：定位器唯一性/可见/可操作、业务断言可执行、联动可复现校验报告；不通过则失败关闭转人工，不自动回退
⑤ 人工审批指定角色（测试架构师 / 审批人）复核需求映射与断言正确性（R5 按业务后果授权）状态 approved；审批记录入审计（R9）
⑥ 版本化落库资产入中心仓库，带版本、来源指纹、需求版本、审批者、失效策略状态 active；可检索、可复用、可回滚
⑦ 覆盖度度量统计需求→资产覆盖度、联动规则断言覆盖、资产稳定性趋势覆盖度报告；低于阈值触发补充分析

资产治理与生命周期（资产是一等公民，非散落文件）：

  • 状态机：draft → pending_review → approved → active → deprecated；任何状态变更记录操作者与时间（R9）。
  • 版本与溯源：每条资产记录生成版本、来源页面/需求版本指纹、LLM 供应商与模型版本、审批者；支持回滚到历史版本。
  • 失效与重验：需求变更或页面改版（定位器漂移，§8）触发关联资产进入 pending_review，须重验或废弃，不自动沿用旧断言。
  • 可插拔 SPI：需求解析器、页面理解引擎、资产仓库均为 SPI（pw-core 定义契约，可选适配层实现），便于替换 LLM 供应商或需求来源而不改主干（薄层复用既有资产）。
  • 冲突仲裁：多次分析或多人审批产生冲突资产时，以最新 approved 版本 + 需求版本为准，旧版本归档不删除。

质量度量与量化验收（不得用「生成了即可」验收）：

  • 需求覆盖度：已有对应资产的需求条目占比；目标阈值由项目在 P1.5 评审确定。
  • 资产置信度 / 误报率：人工审批驳回率、运行期定位器失效重试率；模型建议被驳回比例须低于上限。
  • 稳定性：定位器在 N 次回归中的命中率；低于阈值自动降为需重验。
  • 审批通过率与时效：审批队列积压、平均审批时长，避免人在回路成为瓶颈。

人在回路、权限与降级：

  • 角色与权限（R5）：需求方（提供/确认需求）、测试架构师（设计资产 schema）、QA（执行审批）、审批人（按业务后果授权高风险操作）；AI 永不自动落库为 active。
  • 责任边界：AI 仅产 draft；approved/active 的责任归属人工审批者，可追溯（R9）。
  • 韧性降级：LLM 不可用 → 流程回退到纯录制骨架 / 手写资产，不阻塞回归 CI；需求缺失 → 仅产出无需求映射的资产并标记 incomplete，供后续补映射。
  • 供应商治理（R9/§8.1）：模型供应商须满足数据驻留、训练/留存条款、成本配额；模型不可用时不得影响既有回归链路。
分析期约束：① 输入须最小化并脱敏（R1/R7）——页面与需求文本默认不发送正文/原始快照全文，仅发送白名单字段（角色、可访问名、结构属性、脱敏后的文本），需求样例中的真实账号/金额/PII 须遮蔽；② LLM 不持有浏览器执行权（R6），禁止用 evaluate/run_code_unsafe 辅助分析；③ 敏感字段（凭据、个人数据、token）按未知即敏感处理，不得进入模型上下文；④ 分析在隔离靶场执行（R4/R8）。

4.7 多语言（NLS）与跨语言资产稳定性

问题本质：被测页面是多语言的，同一元素在 en / zh / … 下可访问名不同。若把文案写进资产 （{@code role=checkbox;name=I agree to the terms}），切语言即全部定位失败——这不是"偶发不稳定"，而是 资产在设计上绑死了一种语言。codegen 早已规避此问题（生成 {@code role=checkbox[name=Nls.t("link.agree")]} 而不是文案），Agent 资产必须沿用同一约定，否则两套资产无法共享同一份 nls 资源。

约定（与 codegen 完全一致，不新增第二套规范）：① nls 文件是 两级结构 {@code { "en": { "key": "value" }, "zh": { … } }}，语言 Key 取自第一层； ② 资产只存 key，运行期按当前语言解析成文案；③ 匹配前把 nls 值归一化为可见文本 （剥 {@code /}、解码 {@code  }、折叠空白），因为页面上只有渲染后的文本； ④ 含模板变量（{@code {{user}}}）的值不能按相等匹配，只能编译成正则。以上四条在 {@code pw-core agent.nls} 中一次性收口，codegen 与 Agent 共用同一实现（{@code NLSUtils.visibleText} 已委托）。

双向流转（分析期 name→key，执行期 key→name）：

阶段输入 → 输出实现

为什么"语言未设置"必须报错而不是降级：静默降级会退化成"用字面文案定位"， 在多语言下表现为只有某种语言全挂，且失败信息完全指不到 NLS——这是最难定位的一类缺陷。 因此 {@code JsonNlsCatalog} 在语言缺失时立刻抛出可操作异常（与 {@code NLSUtils.get} 的强制约定一致）。
验收证据（已跑通）：同一份只含 key 的联动资产，在 {@code ?lang=en} 与 {@code ?lang=zh} 的同一页面下经隔离靶场验证均 PASS（stability=1.0）；另有确定性逻辑测试证明 key 被正确本地化为 当轮 canonical，且 en/zh 观测到不同文案时产出同一个 refId 与同一个首选定位符。
与企业级约束的关系：nls 是界面文案资源，不含业务数据，纳入 R1/R7 白名单无冲突； 但反查索引只保存"可见文案 → key"，不得把值里的业务字段（如带客户名的模板值）写进资产——模板值一律 以 key 形式表达，运行期再结合真实值做正则匹配，避免 PII 随资产扩散。

5. 安全目标与控制（纵深防御，不把应用策略称为安全边界）

MCP 官方明确：它不是安全边界（allowed-origins 不防 redirect、secrets 非安全特性、run_code_unsafe 是 RCE）。本方案采用纵深防御；框架策略只能约束自身动作，不能替代网络出口控制、身份与权限治理或隔离运行环境。

红线（不可违反）设计对策
R1 · 凭据与敏感值最小暴露默认不向 LLM 发送页面正文/任意快照。由集中数据策略对白名单字段进行裁剪和脱敏；未知字段按敏感处理。覆盖 URL、DOM/accessibility、错误、网络摘要、截图及 trace。凭据由独立 secret provider 按引用注入执行器；StepPlan 只允许 secretRef，不能包含原文。禁止宣称 Java 字符串可被可靠“用完即清除”。
R2 · 不提供通用代码执行产品原语集中不提供 evaluate、run_code_unsafe 或可注入脚本的接口。需要诊断的功能以范围受限、类型化的只读 API 实现；不得以双开关代替隔离或将任意代码执行作为受支持能力。
R3 · 网络出站纵深控制框架在每个请求及每一跳重定向上执行协议/origin 策略，并覆盖子资源、iframe、弹窗、表单及下载；拒绝未批准目的地。应用层校验不是安全边界，企业部署必须由代理/防火墙或隔离网络限制出站；测试 DNS/IP 解析和重绑定风险，避免仅凭 URL 字符串放行。
R4 · 上下文隔离在隔离靶场默认使用独立 context；登录态持久化须显式声明并通过 secret provider 管理。定义 browser/context/page 所有权、串行化和清理验证；ConcurrencyGate 不等同于浏览器隔离。
R5 · 按业务后果授权依据业务后果、数据分类和目标环境分类策略，而不是将每次 click/type 都视为同级高危。CI 只允许受版本控制的测试策略与专用账号；敏感业务操作需独立人工审批。审批绑定计划摘要、目标 origin、参数范围、执行身份和有效期；页面提供的 role/name 仅是展示信息，不是授权凭据。
R6 · AI 无执行权AI 输出仅两类：受 schema 约束的 StepPlan、未验证候选 selector。两者都过确定性校验层（§4.3/§4.4）后才生效；AI 永远不能直接调用浏览器原语。
R7 · 快照脱敏采用字段白名单和集中脱敏；密码、token、个人数据、URL 参数、页面正文、异常与网络内容均纳入策略。调用方不得通过步骤级开关关闭安全默认值；敏感级别未知时拒绝发送或按敏感数据处理。
R8 · Mock 与数据不泄漏route_mock 与会话生命周期绑定，收尾强制撤销（沿用 Route 收敛语义）；测试数据走最小权限账号/靶场（对齐 RouteTestBed 模式），不碰生产凭据。
R9 · 最小化审计对每步/每次模型调用记录必要元数据：可信执行器生成的 traceId、计划摘要、身份、策略/审批版本、耗时和结果。参数只记经分类的摘要，不保存 secret、原始页面内容或不必要的完整快照。定义访问控制、保留期限、导出审计和删除流程；审计记录不等于可安全重执行的回放脚本。
红线验收标准：每条红线都有单元/集成/架构测试及运行策略证明；例如敏感 canary 不得出现在模型请求、日志、报告或导出物，未批准请求（含重定向/子资源）必须被阻断。ArchUnit 只能检查结构依赖，不能单独证明运行时安全策略有效。

7. 分阶段路线图（每阶段可独立交付、独立验收）

  • P0 · 受限确定性垂直切片（无 AI）—— 先实现版本化 DSL、少量白名单原语（snapshot/assert_state 及无副作用演示操作）、策略校验和最小审计；只在隔离靶场运行。确认快照能力/资源上限后，再逐步开放写操作。
    验收：确定测试数据和浏览器版本下，受限流程结果可比较；失败即停止并提供脱敏诊断。Trace 只供审计，不直接重放真实写操作。
  • P1 · 意图翻译—— 先结构化录制骨架 → StepPlan；完成数据最小化、网络出口和模型供应商审查后，再评估自然语言 → StepPlan 与 LLM 网关适配层。
    验收：相同规范化输入可比较出等价计划；非法 schema、越权 Action、未知字段和不批准 origin 均被拒绝。
  • P1.5 · 页面理解与测试资产生产（分析期 LLM）—— 结合需求上下文（需求条目 / 验收标准 / 业务规则），用 LLM 对脱敏快照分析，产出带需求映射的元素清单、操作行为模型与联动图谱（§4.6），落库为 Page Object/StepPlan/联动断言草案，并支持需求→资产覆盖度；属资产生成期，不进入运行时。
    验收：资产含需求映射与验证证据、经人工审批落库；输入脱敏（无 secret/PII 进模型）；分析产物不自动成为可信定位器（须过 §4.4 验证）；量化指标（需求覆盖度 / 误报率 / 定位器稳定性）须在 P1.5 评审确定阈值（参考 §4.6.3 / §8.1）；回归期不依赖此 LLM 链路。
  • P2 · 稳定代码生成—— 四层产物模板（Feature/Glue/Steps/PO+方法）+ 编译 + 冒烟 + 落库；产物内嵌 trace javadoc；资产来源新增 §4.6 的页面理解产物。
    验收：生成的工程过 checkstyle、冒烟 1 遍绿、落库后 mvn test 零 LLM 运行。
  • P3 · 定位器治理—— CandidateValidator（目标语义/唯一性/可操作性/业务断言）+ 候选审批和版本化回注。
    验收：候选有来源与验证证据；无法确认时失败关闭并转人工，不自动回退到可能错误的目标。
  • P4 · 治理与企业化—— 策略/审批、运行时安全测试、审计保留与导出治理、CI 集成（生成期与回归期分离）及非功能指标。
    验收：安全集成测试全绿；回归 CI 无 LLM；审计访问受控且可按期限删除；满足已批准的性能/并发/恢复目标。
